**踩到的坑（重要）**
- sql.js 的 `db.export()` 内部是「关连接 → 读文件 → 重开连接」，**连接级设置会被清空**：`PRAGMA foreign_keys` 回到 OFF、`create_function` 注册的 cos_sim / vec_norm 也没了。所以每次 export 之后必须调 `shutaHome.syncConnection()` 重新装上——否则 1-3-2 外键任务和 6-x 向量任务会悄悄失效（这个 bug 是 headless 全量跑任务时才暴露的，Node 自测发现不了）
- **"语句报错了却算通过"的坑（用户实测反馈）**：原来 `check.uses` 只匹配"你敲过的 SQL 文本"，不看数据库到底接受没接受 —— 表上次会话就建好了、这次重跑报 `table pets already exists`，照样打勾。修法：① `run()` 改成 `dbRunner.execAll()` 逐条执行、逐条记历史（哪条成功哪条报错清清楚楚，遇错即停）；② `uses` 改成**必须有一条执行成功的语句**匹配，只被拒绝过就判失败，并区分提示"还没做过"vs"这条语句被数据库拒绝了：<报错>"；③ 报错框里显示"出错的语句"；④ 失败反馈针对 already exists 给出"重置数据库 / 看状态面板"的指引；⑤ 已打勾的卡不会因为一次失败掉勾，但会说明。自测脚本加了回归：**先把对象建好、清空历史、再跑同一段 SQL**，任何带 uses 的任务都不许通过（64/64 通过，问题 0 条）
- 任务校验别写死期望值：同学按自己的顺序做，前面的 INSERT/DELETE 会改数据；只读类任务统一用 `fn + sameAsQuery` 跟「当下真实状态」比
- 页面数据库存在 localStorage：同一张卡重复跑建表语句会撞 `table already exists`（1~2 章也是这样），界面失败提示里已引导「重置数据库」
- **双击打开（file://）跑不起来**：浏览器不让 fetch 本地 .wasm，sql.js 报 "both async and sync fetching of the wasm failed"。解决：把 wasm 原样转成 base64 生成 `vendor/sqljs/sql-wasm-b64.js`（880KB），file:// 时走 `initSqlJs({ wasmBinary })` 内联启动；http 下仍走原来的 .wasm（不会多加载这 880KB）。shutaHome.bootSql() 负责两条路互相兜底，状态栏会标注"本地文件模式：用的是内联 WASM"
